## Stage A — a Spout-shaped shared texture exists in the guest

Independent sender, no VRChat involved (`src/guest/spoutpair.c`, run through
`src/guest/run-probe.sh`, which reuses the game's exact env from `/proc/<VRChat.exe>/environ`):

```
ok   D3D11CreateDevice                                    hr=0x00000000
     adapter: Apple M5 (vendor 106b device 0000)
ok   CreateTexture2D MISC_SHARED (sender)                 hr=0x00000000
     1280x720 R8G8B8A8_UNORM
ok   QueryInterface(IDXGIResource)                        hr=0x00000000
ok   IDXGIResource::GetSharedHandle                       hr=0x00000000
     shared handle = 0x40000182
```

DXMT accepts `D3D11_RESOURCE_MISC_SHARED` + `BIND_RENDER_TARGET` and returns a legacy shared handle. This
was the single largest technical risk (Metal may refuse a shared, private, render-target texture) and it
does not happen here.

## Stage B — a second process reads changing frames from it

`spoutpair.exe --send` and `spoutpair.exe --recv` in two separate guest processes:

## Stage C/D in isolation — Syphon publish → discover → receive, without the VM

`build/syphon_test_send --name SpoutBridgeTest` and `build/syphon_test_recv`:

```
attached: name=SpoutBridgeTest uuid=info.v002.Syphon…
t=  1.1s frames=31 1280x720 mean RGB=(80,80,59) A=255 chk=4baa47dc
…
receiver done: 1 server(s), 146 frame(s)
```

Changing checksums every second, ~30 fps, no VM involved. Note: Syphon's server answers discovery on the
thread that created it, so the publisher must pump a run loop — a plain `usleep` loop silently never
appears in `SyphonServerDirectory` (found the hard way; the bridge uses a `CFRunLoopTimer`).

## Stage E — real VRChat, independent camera view

VRChat camera in Stream mode with Spout Stream on:

```
15:41:06.345 newSharedTexture 640x360  fmt=BGRA8Unorm  … ACCEPTED   (camera helper texture)
15:41:06.371 adopting 640x360 as the source (will confirm it is live)
15:41:14.658 newSharedTexture 1280x720 fmt=RGBA8Unorm  … ACCEPTED   (the Spout stream)
15:41:14.672 source switched to the live 1280x720 texture
```

Syphon client: `1920x1080` when VRChat's Stream Resolution was 1080p, `1280x720` at 720p, ~30 fps in both.
OBS's `mac-syphon` source shows the **camera view only** — no game window, no UI, no desktop
(`evidence/obs-vrchat-720p.png`, `evidence/obs-after-receiver-restart.png`).

Alpha: the camera is masked so the background is transparent and it arrives intact —
`alpha extrema (0,255)`, 86.8 % of pixels fully transparent / 13.1 % fully opaque at 720p
(87.5 % / 12.5 % at 1080p). `evidence/vrchat/frame_720p_over_blue.png` composites the received frame over
blue to show the preserved alpha, not a black background.

Orientation: OBS draws Syphon frames bottom-up, so the bridge publishes with `flipped:YES` (`flip=1`).
With `flip=0` OBS rendered the camera upside down (observed live during the first injected run); with
`flip=1` it is upright, as in `evidence/obs-vrchat-720p.png`.

## Measurements

### 1280×720, 30 fps baseline — 5 minutes

| Metric | Value |
| --- | --- |
| Frames delivered to a Syphon client | min 25.8 / **mean 30.0** / max 30.9 fps over 291 s |
| Worst inter-frame gap | 101.6 ms (one 3-frame hiccup in 291 s); no second below 25 fps |
| Source update rate (GPU probe) | 30.0/s, i.e. VRChat really produces 30 new frames/s |
| OBS CPU | mean 5.4 %, max 10.2 % |
| `steamac-vm` CPU (whole VM, game included) | mean 111.6 %, max 139.2 % |
| Raw data | `evidence/stability/fps-vrchat-720p.csv`, `host-vrchat-720p.csv` |

### 1920×1080 — 10 minutes

| Metric | Value |
| --- | --- |
| Frames delivered | min 29.1 / **mean 30.0** / max 31.1 fps over 579 s |
| Worst inter-frame gap | 57.5 ms (≈1.7 frame intervals) |
| OBS CPU | mean 4.5 %, max 6.0 % |
| `steamac-vm` CPU | mean 110.9 %, max 136.4 % |
| Raw data | `evidence/stability/fps-vrchat-1080p.csv`, `host-vrchat-1080p.csv` |

`steamac-vm` RSS fell from 3.4 GB to 1.7 GB over the run — that is the guest's ballooned RAM being
returned, not a leak; the bridge itself allocates only a few small probe textures.

### Latency — not measured optically

The bridge adds a bounded amount, not a measured glass-to-glass number:

* publish is capped at 30 fps, so a frame waits **≤ 33 ms** for the next publish tick (measured interval
  min 33.6 ms, mean 35.7 ms, max 57.5 ms over the 10-minute run — i.e. no queueing);
* the Syphon publish is one GPU blit at 720p (sub-millisecond) plus Syphon's Mach-message hand-off;
* OBS then composites on its own 30 fps tick.

A true capture-to-display figure would need a physical camera filming source and display, or in-guest
timestamp instrumentation; neither was done, so no number is claimed.

## Recovery behaviour

| Scenario | Result |
| --- | --- |
| OBS quit and relaunched while VRChat streams | reconnects by itself, 30.5 fps measured immediately after (`evidence/obs-after-receiver-restart.png`) |
| VM/launcher restarted (new Syphon UUID) | OBS matches by name+app and reconnects — observed at 15:18 after a launcher restart |
| VRChat changes Stream Resolution (destroys + recreates the sender) | with the first build the bridge kept publishing the dead texture (frozen frame, `update 0.0/s`, identical frame hashes). **Fixed**: selection is now liveness-driven; verified with a controlled recreate (1280×720 → 960×540 switch in 8 ms) and with real VRChat (640×360 helper → 1280×720 Spout) |
| Spout Stream switched off | the sender stops writing → `update 0.0/s`, published frames become identical, OBS shows the last frame frozen (by design, so the source does not vanish) |
| Spout Stream switched back on | a new live shared texture is adopted within ~15 ms of creation (`15:41:14.658` → `15:41:14.672`) |

## Not verified / explicitly out of scope

* **Glass-to-glass latency** — no optical measurement (see above).
* **A discrete off→on pair with the fixed build** — the fixed build was validated with a controlled
  sender recreate and with VRChat's own 640×360→720p switch; the earlier VRChat off→on pair (15:36) was
  what exposed the stale-selection bug, and that bug is what the fix was validated against.
* **VRChat's multi-camera / Camera Dolly streams** (`VRCSender2…`, alpha on secondary cameras) — not tested;
  the bridge would take the largest live texture, so multi-stream would need a selection rule.
* **Other Spout senders** (e.g. a browser, a media player) — untested.
* **Launching the launcher normally after injection** — verified that a normal launch has no dylib
  (`vmmap`), so no residue; but the launcher's own update path was not exercised.
* **Non-OBS Syphon consumers** — `flip=1` is tuned for OBS; Syphon Recorder etc. were not tested.
* **Launcher updates** — if a future launcher is hardened or signed with library validation,
  `DYLD_INSERT_LIBRARIES` will be refused; the fallback (rebuild `libwmtr_host.dylib` with a texture-export
  call, as the fork's VR path already does with `WMTVRSubmit`) is designed but not implemented here.
